01 — The shift

An event is evidence.
A box is context.

Stateless processing works until the answer depends on what came before. Then correlation leaks into handlers, stores, retries, and one-off workflows. Boxing gives that waiting and gathering a domain name.

Event-centric

“What should happen because this event arrived?”

Box-centric

“What does this complete context tell us?”

02 — The lifecycle

Four moves.
One richer unit.

Boxes sit between arrival and business processing. They make correlation explicit, reusable, and legible in the language of the domain.

01 / ARRIVE

Receive the event

The stream remains the input. Boxing changes when meaning is assigned.

02 / ROUTE

Choose its boxes

Rules use domain identifiers and meaning. One event may belong to several boxes.

03 / CLOSE

Wait deliberately

Each box accumulates context until its own closing policy is satisfied.

04 / PROCESS

Open as a group

A separate process consumes the closed box as one domain-level input.

03 — Closing policies

Context needs
a boundary.

A box does not wait forever. Its domain decides when the collection has become useful enough—or complete enough—to process.

idle_for(30m)

Sliding expiry

Close after activity stops for a meaningful interval.

count >= 100

Maximum size

Bound a group when volume itself defines the batch.

on(order.confirmed)

Closing event

Let an explicit domain event declare the context complete.

any_of(...)

Combined policy

Compose boundaries so the box reflects real domain timing.

04 — Overlapping meaning

The same event can tell more than one story.

A cart update belongs to the order being built. It can also belong to the customer session that began with a search. Boxes are views of context, not exclusive buckets.
